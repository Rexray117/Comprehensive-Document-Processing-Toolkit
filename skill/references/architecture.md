# 架构设计

## 一、分层结构

```
┌──────────────────────────────────────────────────────────────────────────┐
│  调用入口层                                                               │
│  ┌────────────────┐ ┌────────────────┐ ┌──────────────────────────────┐  │
│  │ core/cli.py    │ │ dispatcher.run │ │ handlers/xxx.py (独立运行)    │  │
│  │ 统一命令行      │ │ Python API     │ │ python handlers/docx_h...   │  │
│  └───────┬────────┘ └───────┬────────┘ └──────────────┬───────────────┘  │
└──────────┼──────────────────┼─────────────────────────┼──────────────────┘
           │                  │                         │
           └──────────────────┴─────────────┬───────────┘
                                            ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  调度层  core/dispatcher.py                                              │
│  · Request 归一化（dict / CLI / JSON 三形态 → 统一对象）                   │
│  · module="auto" 时按文件真实类型路由（registry.resolve）                  │
│  · 异常兜底：任何异常都转成 Response 信封，run() 永不抛异常                  │
│  · 批量执行 run_batch（目录遍历 + 类型过滤 + 续跑）                         │
└───────────────────────────────────┬──────────────────────────────────────┘
                                    ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  注册层  core/registry.py                                                │
│  · 扫描 handlers/ 目录，自动发现 BaseHandler 子类并实例化（热插拔）          │
│  · 记录加载失败原因而非静默忽略（doctor 可查）                              │
│  · 扩展名 / kind → 模块 的路由表                                          │
└───────────────────────────────────┬──────────────────────────────────────┘
                                    ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  契约层  core/base.py                                                    │
│  · BaseHandler（元类自动收集 @action）                                    │
│  · ActionSpec（动作自描述：参数表 / 是否产文件 / 是否改输入）                │
│  · ActionContext（统一提供 读参数 / 读输入 / 写产物 三件事）                │
│  · dispatch()：校验 → 备份 → 计时 → 组装 Response                        │
└───────────────────────────────────┬──────────────────────────────────────┘
                                    ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  模块层  handlers/                                                        │
│  pptx_handler   docx_handler   xlsx_handler   html_handler  image_handler │
│  每模块统一实现 probe / read / analyze / transform / edit 五个动作          │
└───────────────────────────────────┬──────────────────────────────────────┘
                                    ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  能力层（跨模块共享，无业务耦合）                                           │
│  core/utils.py     类型嗅探（OOXML 容器→魔数→扩展名）、路径、文本统计、分词   │
│  core/textops.py   跨 run 文本替换算法（PPTX/DOCX 共用）                   │
│  core/runtime.py   依赖探测、外部工具探测、doctor 报告                       │
│  ocr/engines.py    多后端 OCR（rapidocr → tesseract → easyocr 自动降级）    │
└──────────────────────────────────────────────────────────────────────────┘
```

**依赖方向严格单向向下**：模块层依赖契约层与能力层，契约层不反向依赖任何 handler。
`core/` 中没有任何一行代码 import 具体 handler，因此删掉/新增 handler 不会波及框架。

## 二、请求生命周期

```
run(payload)
  │
  ├─ Request.from_dict()              ── 归一化字段（兼容 op/method、path/file 等别名）
  │
  ├─ registry.resolve(input)          ── module=auto 时：读文件头 8KB
  │                                     · ZIP 容器内是否有 ppt/presentation.xml / word/document.xml / xl/workbook.xml
  │                                     · 否则看魔数（filetype）
  │                                     · 再退回扩展名
  ├─ registry.require_handler(module) ── 未注册模块 → UnsupportedError（带可用模块列表）
  │
  ├─ handler.dispatch(action, ...)
  │    ├─ resolve_action()            ── 支持别名；动作不存在 → ActionError（列出可用动作）
  │    ├─ 输入存在性校验               ── InputError（带排查提示）
  │    ├─ modifies_input → backup_file()  ── 自动生成 _bak 备份
  │    ├─ 构造 ActionContext          ── 参数读取器负责类型转换与越界校验（ParamError）
  │    ├─ 计时执行动作方法
  │    └─ 组装 Response（data + artifacts + warnings）
  │
  └─ 异常出口
       · ToolkitError → 带 code/hint/details 的结构化错误
       · 其它异常     → INTERNAL_ERROR（保留类型名，便于定位）
```

## 三、关键设计决策与取舍

| 决策 | 选择 | 理由 | 放弃了什么 |
| --- | --- | --- | --- |
| 动作命名 | 五个动词跨模块统一 | Agent 只需记 5 个词即可操作 5 类文件；批量调度可复用同一 action | 个别模块特有的强语义动词（如 `render` 降为 `transform` 的 `op`） |
| 重依赖导入时机 | 动作函数内部惰性导入 | 零依赖环境下 `list` / `cap` / `doctor` 仍可用；缺一个库不会让整个工具不可用 | 首调用有极小的导入开销（可忽略） |
| 文件类型判定 | 容器 → 魔数 → 扩展名 三级 | 改名的 `.pptx` 也能正确识别；避免据此产生静默错误处理 | 需要读文件头（一次 IO） |
| 错误表达 | 结构化错误码 + `hint` 带修复命令 | Agent 可自愈（照抄安装命令）；无需人工查文档 | 响应体略大 |
| 危险操作 | `edit` 默认就地保存 + 自动 `.bak` 备份 | 用户预期「改了就是改了」；备份兜底 | 目录里会多出 `.bak`（可 `-p backup=false` 关闭） |
| 幻灯片/文档遍历 | 直接遍历 XML 子元素而非库的高级封装 | python-docx 的 `doc.paragraphs` 会漏掉表格位置信息，导致正文顺序错乱 | 需自行处理少量命名空间细节 |
| 图像语义识别 | 本地不做 VLM，输出「视觉桥接载荷」 | 本地 VLM 需 GPU + 数 GB 权重，与「纯 pip 离线轻量」定位冲突；桥接后质量随调用方模型升级 | 本工具自身不产出语义描述，需调用方补一步 |
| OCR | 多后端可插拔 + 自动降级为 warning | OCR 是唯一没有「纯 pip 标准答案」的能力；硬绑定某一家会让技能在多数环境直接不可用 | 需要维护 3 套适配代码 |
| 文档化 | API 手册从代码契约自动生成 | 手写文档必然随迭代腐化；生成保证「文档 = 实现」 | 文档可读性略逊于精雕的手册 |

## 四、错误处理策略（三级）

1. **可自愈错误 → 抛结构化异常**
   缺依赖（`DEPENDENCY_MISSING`，hint 带 pip 命令）、参数越界（`PARAM_INVALID`）、
   文件损坏（`INPUT_INVALID`）。调用方照 hint 执行即可。
2. **可降级情况 → 记录 warning 并继续**
   `xlsx` 公式无缓存值、图片 OCR 后端缺失、HTML 内联时遇到外链资源、
   LibreOffice 缺失导致跳过渲染。**主流程不中断，结果依然可用**。
3. **未预期异常 → 兜底为 INTERNAL_ERROR**
   附带异常类型名，便于快速定位到是哪个模块的哪一步。

## 五、可扩展性的三个抓手

| 想扩展什么 | 改哪里 | 需要动框架代码吗 |
| --- | --- | --- |
| 新增文件类型（如 PDF、Markdown） | 新建 `handlers/xxx_handler.py` | 不需要，自动发现 |
| 新增某个动作（如 PDF 拆分） | 在对应 handler 里加一个 `@action` 方法 | 不需要 |
| 新增 OCR 后端 | 在 `ocr/engines.py` 加 `recognize_xxx()` 并登记到 `_ORDER` 与 `available_backends()` | 不需要 |

详见 `extension-guide.md`。
